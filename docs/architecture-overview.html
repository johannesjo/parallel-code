Engineering / Architecture

Architecture at a glance.

Parallel Code is an Electron control plane that turns one repository into many isolated agent workspaces. SolidJS owns interaction and durable application state; Electron owns privileged work; Git worktrees are the default unit of task isolation.

Electron 40 SolidJS 1.9 TypeScript 5.9 Desktop + mobile companion
00

The organizing rule: the renderer decides what the user wants; the main process decides how to perform it safely on the host. The preload bridge and IPC manifest are the contract between them.

01 / System shape

One app, two authority levels.

The desktop renderer is deliberately unprivileged. It composes the workspace, holds the reactive model, and requests capabilities. Electron main owns privileged process, filesystem, Git, network-server, and operating-system integration work; ordinary web capabilities such as clipboard writes can remain in the renderer.

P / 01

Renderer-led product flow

App.tsx, domain store modules, and components coordinate normal task creation, navigation, review, and persistence.

P / 02

Main-process authority

IPC handlers validate requests, then call narrow Git, PTY, file, Docker, updater, notification, remote, and MCP modules.

P / 03

Worktree isolation

A standard task receives a branch and .worktrees/<branch> directory, so agents can run concurrently without sharing a working tree.

02 / Task lifecycle

From intent to isolated agent.

A worktree-isolated task crosses the boundary to materialize its Git workspace and again when the mounted terminal asks main to spawn the selected agent. Persistence and later stream/control operations use the same IPC boundary; the store is updated only after required setup succeeds.

01

Capture intent

NewTaskDialog resolves project, agent, base branch, isolation, Docker, prompt, and coordinator options.

02

Isolate work

store/tasks.createTask invokes CreateTask. Main validates the request, creates a slugged branch, and adds the worktree.

03

Publish state

The renderer inserts normalized Task and Agent records, appends the task order, and selects the new workspace.

04

Attach terminal

Reactive render mounts TaskPanel → TaskAITerminal → TerminalView. The terminal opens a UUID output channel and invokes SpawnAgent.

05

Stream both ways

Main batches base64 PTY output to xterm. Input and resize return over IPC; pause and resume provide backpressure when rendering falls behind.

06

Review & land

Git IPC supplies status and diffs. Merge, push, or close actions validate repository state before optional agent, worktree, and branch cleanup.

Three isolation modes

worktree creates an app-owned branch/worktree; direct uses the current project branch; none supports non-Git folders. Imported worktrees remain user-owned and are not deleted during normal cleanup.

Reload without process loss

PTY sessions live in main and are keyed by agent ID. A renderer reload can attach a new output channel, resize and resume the existing process, then replay its bounded scrollback.

03 / State & data

Ownership is explicit.

The renderer is authoritative for product state; main owns live resources. Persistence serializes a deliberate subset of the Solid store, while task artifacts stay with the repository that produced them.

Restore order matters

Startup loads agents and state, restores coordinator servers before their children, reloads plan content, validates project paths, then starts autosave and live subscriptions.

04 / Contracts

Small boundaries, typed payloads.

Parallel Code uses different contracts for request/response IPC, high-volume streams, the phone WebSocket, and MCP coordination. Each lives close to the process boundary it protects.

electron/ipc/channel-manifest.json

Named IPC capabilities

The manifest feeds the typed IPC export. The preload holds an exact literal allowlist, checked by tests and again during development startup.

  • Renderer requests use invoke<T>().
  • Main pushes lifecycle events with webContents.send.
  • Handlers validate primitives and channel-specific identifiers, branch names, paths, URLs, and hashes.
src/lib/ipc.ts

Scoped stream channels

Channel<T> creates a UUID topic, serializes itself as a channel ID, and subscribes to channel:<uuid>. PTY output and command progress use this path.

  • PtyOutput is a Data / Exit discriminated union.
  • PTY bytes are base64 encoded across Electron IPC.
  • Disposal removes the exact listener.
electron/ipc/shared-types.ts

Cross-process DTOs

Task creation, Git status, diffs, commits, coverage, PR checks, and agent definitions are declared in main-owned pure types and re-exported to the renderer.

  • Application entities stay in src/store/types.ts.
  • Renderer runtime imports from electron/ are limited to explicitly allowlisted shared modules.
  • Migrations validate persisted data at runtime.
electron/remote/protocol.ts · electron/mcp/types.ts

Network and coordinator protocols

Remote WebSocket messages and coordinator task/landing shapes have dedicated discriminated unions and runtime validation appropriate to untrusted input.

  • WebSocket input, resize, kill, subscribe, output, and status messages.
  • Coordinator task state, verification, landing, and notification metadata.
  • Token class and ownership checks happen server-side.
05 / Optional planes

Phone access and agent delegation.

One local HTTP/WebSocket server supports two distinct features: a mobile companion and token-protected MCP coordination. The protocols share transport infrastructure, not authority.

src/remote/ ↔ electron/remote/

Phone companion

A second Solid SPA is served from Electron main. It lists agents, streams selected terminal output and scrollback, accepts interaction, edits notes, and creates tasks after PIN pairing.

Phone SPA → HTTP / WS → Remote server → PTY / renderer bridge
  • Manual access binds to the network; the QR-carried token can list agents, stream or write active terminals, and read or edit task notes.
  • PIN pairing mints an in-memory elevated token that additionally permits top-level task creation.
  • Task creation round-trips through the renderer to preserve the normal store path.
electron/mcp/ ↔ electron/remote/server.ts

MCP coordinator

A bundled Node script speaks MCP over stdio to coordinator and task-scoped subtask CLIs, selects a role-specific tool set, and delegates calls over authenticated HTTP to a lazy-loaded main-process Coordinator.

Agent CLI → MCP stdio → Token-auth HTTP → Coordinator
  • Coordinator tools create, inspect, prompt, wait for, merge, and close subtasks; task-scoped subtask tools expose land_self and legacy signal_done.
  • On macOS, a Docker coordinator that starts the otherwise-stopped shared HTTP server binds it to 0.0.0.0 for container access, exposing the bearer-token-protected port to LAN interfaces. An already-running loopback server is reused rather than rebound.
  • Main directly uses task, Git, and PTY primitives, then mirrors events to the renderer.
  • Persisted coordinator tasks are registered before child-task hydration at startup.

Why orchestration has two paths

Human-created tasks
Renderer-led. Store actions call IPC, then publish the resulting task and agent records into Solid state.
Coordinator-created subtasks
Main-led. The Coordinator uses backend primitives independently of the UI, then sends lifecycle events so the renderer can mirror the task.
Phone-created tasks
Bridged back to the renderer. This deliberately reuses the human-created path instead of duplicating its store orchestration in the remote server.
06 / Guardrails

Trust the boundary, validate the crossing.

The security model trusts the bundled renderer to call allowlisted desktop capabilities. Context isolation, narrow preload exposure, navigation checks, and validation limit—but do not eliminate—the impact of a renderer compromise.

01

Renderer containment

Context isolation is enabled and Node integration is disabled. Popup creation is denied in-window, with HTTP(S) targets handed to the system browser. Top-level navigation currently accepts URLs beginning with the configured development origin and any file:// URL; treat this as routing policy, not an origin-exact containment boundary.

02

Explicit capabilities

The preload exposes only IPC subscription/invocation, zoom, and dropped-file path resolution. Named channels must appear in both manifest and allowlist.

03

Command and path validation

Main applies channel-specific checks to commands, branches, hashes, URLs, filenames, paths, and MCP UUIDs. Git and child-process work uses argv APIs; shell metacharacters are rejected where relevant.

04

Network authority classes

Coordinator, subtask, mobile, and paired tokens have different routes and ownership checks. Pairing PINs are short-lived, bounded-attempt, and single-use.

05

Recoverable writes

Application state and keybindings use validate → temp file → backup → rename. MCP configuration is written atomically with restrictive permissions and excluded from Git.

!

Trust-model edge

Allowlisted filesystem capabilities accept validated absolute paths but are not scoped to a project root. A compromised renderer could exercise those capabilities; isolation, navigation controls, and the narrow preload remain critical.

07 / Code map

Find the owning module first.

The repository is organized by process boundary first and domain second. Normal feature work should extend the existing domain store and IPC handler rather than create a new cross-cutting layer.

Repository landmarks

  • src/App.tsxDesktop renderer shell, startup, global subscriptions and shortcuts.
  • src/components/Task workspace, xterm surfaces, sidebar, diff/review UI, dialogs.
  • src/store/Reactive model, domain actions, persistence, status and synchronization.
  • src/lib/Renderer infrastructure: IPC, themes, terminal helpers, focus, parsing.
  • src/remote/Independent mobile Solid SPA, REST helpers, WebSocket client and auth.
  • src/arena/Independent arena state machine and screens, reusing terminal/review parts.
  • electron/main.tsDesktop process entry, environment repair, BrowserWindow and permissions.
  • electron/ipc/Capability registration and privileged PTY, Git, persistence and watcher modules.
  • electron/remote/HTTP/WebSocket server, protocol validation, pairing and token scopes.
  • electron/mcp/Stdio bridge, HTTP client, coordinator lifecycle, validation and landing.

08 / Build & change

Three artifacts, one desktop release.

Production combines the desktop renderer, the remote SPA, compiled Electron main, and a CommonJS MCP bridge. electron-builder packages those outputs for macOS and Linux only.

npm run dev

Development loop

Compile Electron main, bundle the MCP server, start Vite on port 1421, then launch Electron against the live renderer URL.

  • Vite ignores nested .worktrees to avoid self-triggered reloads.
  • Electron reload can reattach to main-owned PTYs.
  • Development state uses a separate user-data directory.
npm run build

Production packaging

Build both Solid surfaces, compile Electron, bundle the MCP entry, then assemble signed and notarized macOS packages or Linux installers.

  • dist/ — desktop renderer
  • dist-remote/ — mobile SPA
  • dist-electron/ — main process and MCP bridge

Static quality gates

CI runs backend and frontend type checks, lint, format, dead-code and dependency checks, Semgrep rule tests, and Vitest. Separate scripts provide coverage and secret scanning.

Architecture rules are executable

Dependency Cruiser rejects runtime renderer-to-main imports except explicitly allowlisted shared paths, blocks MCP dependencies on renderer components, store, and lib, and rejects circular dependencies. The preload allowlist has its own synchronization tests.
